# Deployment (Render)

`render.yaml` is a Render blueprint describing everything: an API web service, a
webhook worker, a Redis instance and a Postgres database. Both services build the
same `Dockerfile` and differ only in their command.

```
render.yaml
├─ web    ledgerflow-api               node dist/server.js   (health check /health/ready)
├─ worker ledgerflow-webhook-worker    node dist/worker.js
├─ redis  ledgerflow-redis             starter
└─ db     ledgerflow-postgres          basic-256mb
```

## First deploy

1. Push the repository to GitHub and create a **Blueprint** in Render pointing at
   it. Render reads `render.yaml` and creates all four resources.
2. Set the secrets Render cannot generate for you (`sync: false` in the blueprint):

   ```bash
   openssl rand -base64 32     # WEBHOOK_SECRET_KEY — set the SAME value on api and worker
   ```

   `API_KEY_PEPPER` is generated by Render on the API service and referenced by
   the worker, so it exists in exactly one place.
3. Deploy. `preDeployCommand: node dist/infra/migrate.js` applies migrations
   before the new image takes traffic.
4. Create the first organization and admin key. The bootstrap route is refused
   when `NODE_ENV=production` (the process will not even start with
   `BOOTSTRAP_ENABLED=true`), so do this against the production database from a
   trusted shell — for example a one-off Render job running the API image with
   `NODE_ENV=development` and the production `DATABASE_URL`, or by calling
   `POST /v1/api-keys` from an existing admin key.

## Secrets and rotation

| Variable             | Owner            | Rotation consequence                                        |
| -------------------- | ---------------- | ------------------------------------------------------------- |
| `API_KEY_PEPPER`     | Render-generated | **Invalidates every issued API key.** Plan a re-issue window. |
| `WEBHOOK_SECRET_KEY` | You (32B base64) | **Invalidates every stored webhook signing secret** (they are encrypted with it, ADR-0008). Rotate endpoints' secrets afterwards. |
| `DATABASE_URL`       | Render database  | —                                                             |
| `REDIS_URL`          | Render redis     | Auth cache and delivery queue are rebuilt automatically.      |

`TRUST_PROXY` must match the deployment topology: it is the rate-limit key.
Set it to the number of trusted proxy hops in front of the app (Render: `1`) and
never to `true` unless every hop is yours; otherwise a client picks its own
bucket by sending `X-Forwarded-For`.

Both processes must always see the same `API_KEY_PEPPER` and
`WEBHOOK_SECRET_KEY` (`render.yaml` binds the worker's copy of both from the web
service with `fromService`, so they cannot drift). A mismatch shows up as authentication failures or
undecryptable webhook secrets, not as a startup error.

Everything else has a safe default in `src/config/env.ts`; override per
environment as needed (`RATE_LIMIT_MAX`, `RATE_LIMIT_IP_MAX`, `TRUST_PROXY`,
`WEBHOOK_LEASE_MS`, `IDEMPOTENCY_REAP_INTERVAL_MS`, `WEBHOOK_MAX_ATTEMPTS`,
`WEBHOOK_CONCURRENCY`, `OUTBOX_POLL_INTERVAL_MS`, `DATABASE_POOL_MAX`). The
process fails fast at boot on any invalid combination, including the
production-only refusals: default pepper, default webhook key, bootstrap enabled,
or either SSRF escape hatch.

## Migration discipline

Migrations run **before** the new image serves traffic, which means the *old*
image runs against the *new* schema for the length of the deploy. Every
migration must therefore be backward compatible with the previous release:

- add nullable columns, backfill, switch reads, and only drop in a later release
  (expand/contract);
- never rename in place — add, migrate, remove;
- `npm run db:verify` blocks unmarked destructive statements in CI, so removing
  something is a deliberate, reviewed act (`-- allow-destructive`).

Migration `0004` includes a full-table backfill of `entries.organization_id`.
For a large ledger, schedule or pre-stage that backfill in batches before the
deployment so the migration does not compete with peak write traffic.

Rollback is redeploying the previous image, and that is only safe because of the
rule above. There are no down-migrations: rolling a schema backwards on a ledger
risks data, so corrections go forward.

## Operating

- **Health:** `/health/live` never touches dependencies; `/health/ready` probes
  Postgres and Redis and returns `503` when degraded, which is what Render's
  health check uses to keep an instance out of rotation.
- **Logs:** structured pino JSON with `authorization`, secrets and API keys
  redacted; every request and error carries a request id.
- **Webhook backlog:** if the worker is down, outbox rows accumulate as `pending`
  and drain on recovery — no events are lost, delivery is just late. Watch
  `outbox_events` where `status='pending'` and `webhook_deliveries` where
  `status='dead_letter'`.
- **Scaling:** the API is stateless, so scale it horizontally. Run **one** worker
  first; the outbox claim uses `FOR UPDATE SKIP LOCKED` and the delivery unique
  index makes duplicates impossible, so more workers are safe, but Postgres
  connections are the limit before throughput is.

## Other platforms

Nothing in the application is Render-specific: it is a Docker image, a Postgres
URL and a Redis URL. `docker-compose.yml` (`--profile app`) runs the same two
processes locally, and any platform that can run a container with those two
environment variables and a pre-deploy command will work — the only requirements
are that migrations run before the new image takes traffic and that both
processes share the same secrets.
